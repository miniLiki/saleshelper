# AI 产品分析推荐系统任务周期拆解

## 总览

任务周期以 `docs/final-implementation-plan.md` 为主线，按完整业务项目拆分，而不是按“可信问答 MVP”拆分。问答能力只作为 Evidence Pack、报告解释和引用追问的辅助入口，不能作为项目终点。

总体推进顺序：

```text
项目骨架和基础设施
-> 资料权限和数据规范
-> 文档解析和知识抽取
-> 向量检索和图谱关系
-> 产品识别和 Evidence Pack
-> 分析任务工作流
-> 目标市场分析
-> 竞品对比分析
-> 竞品动态沉淀
-> 销售推荐策略
-> 结构化报告输出
-> 质量治理、评估和上线
```

建议节奏：

- 周期 0-1：完成项目可运行骨架、权限、资料上传和元数据规范。
- 周期 2-4：完成文档解析、结构化抽取、向量索引和图谱关系。
- 周期 5-6：完成产品识别、Evidence Pack、分析任务和辅助问答。
- 周期 7-10：完成市场分析、竞品分析、竞品动态和销售推荐。
- 周期 11-12：完成结构化报告、质量治理、评估和上线准备。

每个周期都要产出可验证交付物。第一个正式可交付版本必须跑通“资料接入 -> 知识库 -> 市场分析 -> 竞品分析 -> 销售推荐 -> 报告输出”的业务闭环。

## 周期 0：项目初始化与基础设施

目标：搭建可运行的项目骨架、本地开发环境和基础服务连接。

核心任务：

- 创建 `backend/`、`frontend/`、`infra/`、`docs/`、`samples/` 目录。
- 初始化 FastAPI 后端项目和 React + TypeScript + Vite 前端项目。
- 编写 Docker Compose，启动 PostgreSQL、Redis、Milvus、Neo4j、MinIO。
- 配置 `.env.example`，覆盖数据库、对象存储、模型接口和 JWT 配置。
- 建立后端 `/health`、基础日志、异常处理和配置加载。
- 建立前端基础布局、路由框架和 API client。
- 编写 README、本地启动说明和基础服务排障说明。

交付物：

- 可启动的本地开发环境。
- 后端和前端项目骨架。
- Docker Compose 基础配置。
- `.env.example`。
- README 初稿。

验收标准：

- `docker compose up` 可启动 PostgreSQL、Redis、Milvus、Neo4j、MinIO。
- 后端 `/health` 返回正常。
- 前端可访问基础页面。
- 后端能连接 PostgreSQL、Redis、Milvus、Neo4j、MinIO。
- 新成员可按 README 启动本地环境。

## 周期 1：用户权限、资料规范与上传入口

目标：建立用户权限、资料元数据规范和资料上传入口，为后续知识库建设打底。

核心任务：

- 实现用户表、角色表、权限表、登录接口和 JWT 鉴权。
- 建立管理员、知识维护人员、业务用户、只读用户四类基础角色。
- 实现资料上传接口，原始文件保存到 MinIO。
- 设计并落库 `documents`、`document_versions`、`ingestion_jobs`。
- 支持资料类型、业务类型、所属产品、所属竞品、所属行业、来源、可信等级、权限范围等元数据。
- 前端实现登录页、资料上传页、资料列表页和资料元数据筛选。
- 准备样例资料目录，包括产品资料、客户案例、行业资料、竞品资料和销售 FAQ。

交付物：

- 登录和角色权限能力。
- 资料上传接口和资料列表页。
- 文档元数据表和上传任务表。
- 样例资料集目录结构。
- 资料分类与元数据填写规范。

验收标准：

- 管理员和知识维护人员可上传资料。
- 普通业务用户不能上传或维护资料。
- 文件成功进入 MinIO，PostgreSQL 中有对应 `documents` 记录。
- 资料列表可按产品、竞品、行业、资料类型、可信等级筛选。
- 上传失败时有明确错误提示和任务状态。

## 周期 2：文档解析、清洗与 Chunk 切分

目标：把原始资料转换为带来源元数据的可检索文本切片。

核心任务：

- 使用 Celery + Redis 实现异步解析任务。
- PDF 支持 PyMuPDF / pdfplumber / Docling 中的至少一种解析路径。
- Word 支持 python-docx 或 Docling。
- Excel 支持 openpyxl / pandas，保留 sheet、表头和行列上下文。
- PPT 支持 python-pptx，提取页面文字和备注。
- Markdown/TXT 支持按标题和段落解析。
- 清洗页眉、页脚、重复空白和无效字符。
- 按标题、页码、表格和业务段落切分 chunk。
- 写入 `document_chunks`，保留文件、页码、sheet、标题路径、资料类型、可信等级等元数据。
- 实现解析任务状态、失败原因和重试能力。

交付物：

- 文档解析 Worker。
- `document_chunks` 表。
- 资料详情页，可查看解析文本和 chunk。
- 失败任务重试能力。

验收标准：

- PDF、Word、Excel、PPT、Markdown、TXT 各至少一份样例文件可成功解析。
- chunk 保留来源文件、页码、sheet、标题路径、资料类型和可信等级。
- Excel 表格解析后保留表头和行列上下文。
- 解析失败不影响主服务，可在后台查看失败原因并重试。

## 周期 3：结构化抽取与知识库维护

目标：从资料中抽取产品、参数、行业、场景、痛点、客户案例、竞品和销售材料等候选知识。

核心任务：

- 设计产品、型号、参数、卖点、行业、场景、痛点、客户案例、销售材料、竞品、竞品产品等 PostgreSQL 表。
- 设计 `extraction_candidates`，保存抽取候选、来源 chunk、置信度和审核状态。
- 编写产品资料、参数表、客户案例、竞品资料、行业资料、销售资料的抽取 Prompt。
- 使用 Pydantic 校验 LLM JSON 输出。
- 抽取结果绑定 `source_chunk_id`、置信度、抽取版本和资料类型。
- 管理员可查看、确认、修正或忽略抽取结果。
- 人工确认字段优先级高于自动抽取字段，自动抽取不能覆盖人工确认内容。

交付物：

- 核心知识表。
- 抽取候选表和审核状态。
- 结构化抽取 Worker。
- 产品知识页和候选知识审核页。

验收标准：

- 样例产品资料可抽取产品名称、型号、参数、功能、卖点和适用场景。
- 样例客户案例可抽取行业、痛点、应用场景、解决方案和实施效果。
- 样例竞品资料可抽取竞品名称、产品线、优势、劣势和关键参数。
- 管理员可修正错误字段，修正后不会被自动任务覆盖。
- 每个关键字段都能追溯到来源 chunk。

## 周期 4：向量索引、关键词检索与图谱关系

目标：建立可重建的检索索引和业务关系网络，为 Evidence Pack 服务。

核心任务：

- 接入 OpenAI-compatible embedding API。
- 建立 Milvus `document_chunks` collection。
- 将 chunk embedding 写入 Milvus。
- 支持按产品、竞品、行业、资料类型、业务类型、可信等级、更新时间过滤。
- 实现基础关键词精确检索，覆盖产品名、型号、参数名、竞品名。
- 定义 Neo4j 节点：Product、ProductModel、Competitor、CompetitorProduct、Industry、Scenario、PainPoint、SellingPoint、CustomerCase、SalesMaterial、Document、Chunk。
- 定义 Neo4j 关系：APPLIES_TO、USED_IN、SOLVES、HAS_SELLING_POINT、HAS_CASE、COMPETES_WITH、SUPPORTS、MENTIONS。
- 从 PostgreSQL 正式知识表写入 Neo4j。
- 支持从 PostgreSQL 重建 Milvus 和 Neo4j。

交付物：

- Milvus 向量索引。
- 关键词检索服务。
- Neo4j 基础知识图谱。
- 检索调试接口。
- 索引重建脚本或后台任务。

验收标准：

- 输入自然语言问题可召回相关 chunk。
- 输入产品型号、参数名或竞品名可精确命中相关资料。
- 可查询“某行业适合哪些产品”“某痛点匹配哪些产品”“某产品有哪些竞品和卖点”。
- 检索结果包含 chunk、来源、页码、可信等级和相关分数。
- Milvus 和 Neo4j 可从 PostgreSQL 重建。

## 周期 5：产品识别与 Evidence Pack

目标：建立所有分析任务的统一入口和证据包生成能力。

核心任务：

- 实现 `POST /api/products/identify`。
- 支持产品名称、型号、别名、模糊匹配和向量相似匹配。
- 用户上传新产品资料时，支持创建临时产品对象并进入分析流程。
- 设计并落库 `analysis_tasks`、`analysis_task_steps`、`evidence_items`。
- 实现任务参数解析，包括产品、目标行业、指定竞品、分析目标和输出格式。
- 实现查询改写和多路 query 生成。
- 同时查询 PostgreSQL、关键词检索、Milvus 和 Neo4j。
- 合并、去重、过滤和 reranker 重排序候选证据。
- 生成按产品事实、行业资料、客户案例、竞品资料、销售材料分组的 evidence pack。

交付物：

- 产品识别接口。
- 分析任务基础表。
- Evidence Pack 生成服务。
- 证据包调试页。
- 证据引用编号和资料缺口初步识别。

验收标准：

- 输入产品名称或型号可匹配正确产品。
- 未完全匹配时能给出候选产品和置信度。
- 指定产品后可生成 evidence pack。
- evidence pack 包含来源、页码、可信等级、资料类型和召回分数。
- 参数、价格、客户案例、竞品信息等高风险事实优先来自可信来源。

## 周期 6：分析任务工作流与辅助问答

目标：搭建可追踪、可重试的分析工作流，并保留问答作为证据解释入口。

核心任务：

- 接入 LangGraph 或等价有状态工作流实现。
- 实现分析任务创建、运行、暂停、失败重试和状态查询。
- 每个工作流节点保存输入 JSON、输出 JSON、状态、错误信息和耗时。
- 建立基础节点：product_identification、evidence_pack、quality_check、report_stub。
- 实现 `POST /api/analysis-tasks`、`GET /api/analysis-tasks/{id}`、`POST /api/analysis-tasks/{id}/run`。
- 实现辅助问答接口 `POST /api/chat`，用于追问证据和解释报告结论。
- 问答输出区分事实、分析、推测、建议和资料缺口。
- 保存会话、消息、引用证据和检索调试信息。
- 前端实现分析任务页、任务步骤进度和辅助问答页。

交付物：

- 分析任务工作流框架。
- 任务状态和步骤记录。
- 辅助问答接口和页面。
- 引用来源侧栏。

验收标准：

- 用户可创建并运行一个分析任务。
- 任务每个节点的输入、输出、状态可追踪。
- 失败节点可重试，不需要重跑全部流程。
- 辅助问答能基于 evidence pack 回答，并展示引用来源。
- 资料不足时明确输出缺口，不编造事实。

## 周期 7：目标市场分析工作流

目标：实现产品目标行业、客户画像、应用场景、客户痛点和市场进入策略分析。

核心任务：

- 实现 Reader 节点，读取产品事实包并检索行业资料、客户案例和市场资料。
- 实现 Analyst 节点，分析产品能力与行业需求、客户痛点、采购场景、已有案例之间的匹配关系。
- 实现 Strategist 节点，形成优先进入行业、目标客户类型、主打场景、价值主张和进入策略。
- 实现 Formatter 节点，输出结构化市场分析 JSON。
- 为目标行业排序、客户画像、痛点匹配和进入策略绑定引用来源。
- 前端实现目标市场分析视图。

交付物：

- 市场分析工作流。
- 目标行业排序。
- 目标客户画像。
- 典型应用场景和客户痛点映射。
- 市场机会、进入策略和资料缺口。

验收标准：

- 选择一个样例产品后，可生成目标市场分析结果。
- 行业推荐必须说明产品能力、客户痛点、案例或行业资料依据。
- 分析结果不能只停留在“适合制造业”等泛化表述，需要落到具体场景。
- 资料不足的行业或场景明确标注待验证。
- 关键结论有引用来源。

## 周期 8：竞品对比分析工作流

目标：实现我方产品与竞品的结构化对比、差异化卖点和销售反驳话术。

核心任务：

- 实现 Researcher 节点，检索我方产品资料和竞品资料。
- 未指定竞品时，根据产品类别、行业、场景和历史竞品记录推荐候选竞品。
- 实现 Analyst 节点，按功能能力、技术参数、适用场景、价格区间、部署成本、维护成本、稳定性、交付周期、售后服务、典型客户、认证资质、市场定位等维度对比。
- 实现 Writer 节点，生成我方优势、我方劣势、差异化卖点、竞品风险提示、反驳话术和销售注意事项。
- 缺少资料的对比项标注“资料不足，暂不判断”。
- 前端实现竞品分析页和竞品对比表。

交付物：

- 竞品候选推荐。
- 竞品对比工作流。
- 竞品对比表。
- 差异化卖点。
- 竞品反驳话术和销售注意事项。

验收标准：

- 指定我方产品和竞品后可生成结构化对比表。
- 每个高风险对比项有来源或资料不足标记。
- 不编造竞品价格、参数、客户案例和市场份额。
- 销售话术能对应产品卖点、客户痛点或竞品差异。
- 竞品资料不足时仍能输出清晰资料缺口。

## 周期 9：竞品动态沉淀

目标：将竞品资料、新闻、官网页面和销售反馈抽取为可持续积累的竞品事件库。

核心任务：

- 设计并落库 `competitor_events`。
- 支持上传竞品新闻、网页快照、行业文章、销售反馈和竞品资料。
- 实现竞品事件抽取 Prompt 和 JSON Schema。
- 事件类型覆盖产品发布、参数变化、价格变化、客户案例、合作伙伴、融资并购、市场活动、招聘扩张、行业进入、负面舆情、销售反馈。
- 实现事件去重，生成 `dedupe_key`。
- 按来源、可信等级、时间一致性和内容重复度判断事件可信度。
- 为事件记录影响等级、关联竞品、关联竞品产品和来源 chunk。
- 前端实现竞品动态时间线。

交付物：

- 竞品事件库。
- 竞品事件抽取服务。
- 事件去重和可信度判断。
- 竞品动态时间线页面。

验收标准：

- 上传竞品新闻或销售反馈后，可抽取结构化事件。
- 重复事件不会反复入库。
- 每个事件能追溯来源资料。
- 竞品动态可按竞品、事件类型、时间、影响等级筛选。
- 竞品事件可被后续竞品分析和报告调用。

## 周期 10：销售推荐策略

目标：把产品分析、市场分析和竞品分析转化为销售人员可以直接使用的建议。

核心任务：

- 建立客户画像生成节点。
- 建立客户适配度评分节点，覆盖行业匹配度、痛点匹配度、案例匹配度、竞品替代机会、采购可能性和销售进入难度。
- 建立销售切入点生成节点。
- 建立需求挖掘问题生成节点。
- 建立首次触达话术、产品推荐逻辑、竞品异议回应和成交推进建议生成节点。
- 建立推荐销售材料匹配逻辑，关联销售材料、产品资料、案例和引用来源。
- 前端实现销售策略页。

交付物：

- 客户画像。
- 客户适配度评分。
- 销售切入点。
- 需求挖掘问题清单。
- 推荐话术和异议处理话术。
- 推荐销售材料列表。

验收标准：

- 输入产品和目标行业后，可生成通用销售策略。
- 输入目标客户或具体行业后，可生成更具体的客户适配度和销售建议。
- 每个评分维度说明依据来源。
- 销售话术不泛泛而谈，能对应痛点、卖点、案例或竞品差异。
- 推荐材料能回到资料库中的具体文件或片段。

## 周期 11：结构化报告工作台与导出

目标：把各分析节点结果整合为可查看、可复用、可导出的结构化产品分析报告。

核心任务：

- 设计并落库 `analysis_reports`、`report_sections`、`report_exports`。
- 实现“中间结果汇总 -> 事实校验 -> 结构化 JSON -> Markdown 渲染”的报告生成链路。
- 报告章节覆盖产品概述、核心能力、目标市场、客户画像、应用场景、痛点匹配、客户案例、竞品对比、竞品动态、销售策略、推荐材料、资料缺口和引用来源。
- 前端实现报告工作台，包括左侧目录、中间报告正文、右侧引用来源和资料缺口。
- 支持报告版本管理和历史报告查看。
- 支持 Markdown 导出；Word 或 PDF 导出可按团队资源选择其一。
- 支持在报告中发起追问，调用辅助问答解释报告结论。

交付物：

- 结构化报告生成服务。
- 报告工作台。
- 报告版本和历史记录。
- 报告导出能力。
- 引用来源侧栏。

验收标准：

- 分析任务完成后可生成完整报告。
- 报告包含产品概述、目标市场、客户画像、竞品对比、销售策略和引用来源。
- 报告关键事实有引用编号，可点击查看原文片段。
- 事实、分析、推测、建议和资料缺口有清晰区分。
- 报告可导出并保留引用来源。

## 周期 12：质量治理、评估与上线准备

目标：建立质量闭环，完成完整业务项目上线验收。

核心任务：

- 实现质量检查规则：引用覆盖、参数来源、竞品事实来源、销售建议依据、资料缺口识别、输出结构合规。
- 保存质量检查结果到 `quality_checks`。
- 实现用户反馈接口，支持对报告章节、引用来源、销售建议和问答结果反馈。
- 建立 30-80 条评估任务，覆盖产品识别、市场分析、竞品对比、销售建议、竞品事件、报告引用和资料不足场景。
- 统计产品识别准确率、检索命中率、事实准确率、引用正确率、市场分析可用率、竞品对比可用率、销售建议可执行率、报告结构完整率。
- 完成 Docker Compose 部署验证。
- 编写部署文档、运维说明、上线检查清单和测试报告。
- 梳理上线前风险、待补资料清单和后续优化 backlog。

交付物：

- 质量检查模块。
- 用户反馈闭环。
- 评估集和评估脚本。
- 系统测试报告。
- 部署文档和运维说明。
- 上线检查清单。
- 待补资料清单。

验收标准：

- 标准评估任务可批量运行。
- 产品参数类事实准确率达到 90% 以上。
- 报告关键事实引用覆盖率达到 90% 以上。
- 竞品资料不足场景不能编造参数、价格、客户案例或市场份额。
- Docker Compose 环境可完整跑通资料接入、知识库、市场分析、竞品分析、销售推荐、报告输出和反馈回流。
- 业务用户可以查看报告、追问结论、导出报告并提交反馈。

## 整体验收路径

最终验收应使用真实或接近真实的样例资料：

- 至少 10 份产品资料。
- 至少 5 份客户案例或销售 FAQ。
- 至少 3 份行业资料。
- 至少 3 份竞品资料。
- 至少 3 份竞品动态资料或销售反馈。
- 至少 30 条标准评估任务。

验收链路：

```text
上传资料
-> 解析成功
-> chunk 生成
-> 结构化抽取
-> 人工审核修正
-> embedding 写入
-> 图谱关系写入
-> 创建产品分析任务
-> 产品识别
-> 生成 evidence pack
-> 目标市场分析
-> 竞品对比分析
-> 竞品动态抽取
-> 销售推荐策略
-> 结构化报告输出
-> 检查引用和资料缺口
-> 报告导出
-> 提交反馈
```

最终通过条件：

- 完整业务链路稳定跑通。
- 产品、参数、客户案例、竞品和销售建议都能追溯来源。
- 市场分析和竞品分析不是泛化文本，而是结构化业务结果。
- 资料不足时系统明确输出缺口，不编造事实。
- 管理员能修正知识，修正结果能进入后续分析。
- 业务人员认为报告和销售建议具备试用价值。

## 默认假设

- 任务周期按完整业务闭环递进，不按问答 MVP 递进。
- 首期采用 PostgreSQL + Milvus + Neo4j + MinIO + Redis。
- 工作流编排采用 LangGraph 或等价实现。
- 首期外部市场数据以人工上传和网页快照为主，不强依赖自动爬虫。
- 首期报告至少支持 Markdown 导出，Word 或 PDF 导出按实施资源选择。
- 后续若进入实施阶段，每个周期都应单独拆为 issue 或 sprint backlog。
